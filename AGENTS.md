# Agent Operating Guide

This repo is a GutConference Online PHP/JSON full-stack CMS for shared hosting. It is not a SPA, not a SQL app, and not a public event marketplace.

## Core Shape

- Frontend/UI: modern HTML and CSS in `views/`, fed by JSON/schema data. PHP runs the shared-hosted app and binds data, but UI decisions should be HTML/CSS-first.
- Backend: PHP controllers and services in `app/`.
- Database: JSON collections in `storage/data/`.
- Schema: `storage/schema/collections.json` is the source of truth for collection shapes, admin fields, media fields, and agent-visible context.
- Admin: owner tools for events, sections, speakers, agenda, venues/maps, registrations, notifications, media, integrations, environment, settings, audit logs, and project map. Admin is already fine-tuned — do not add admin features unless the user explicitly asks.
- Agent workflow: `AGENTS.md`, `Design.md`, and `.agents/skills/`.

## Project Status and Mindset

- The project is **already complete** in scope. Most of the work from now on is small surgical tweaks, not new features.
- User-facing flows come first. Do not get pulled into admin work.
- Schema is the source of truth. Read the schema before you propose a change; update the schema before you change code that depends on a collection shape.
- If existing code already covers a use case, **extend it** — do not create a parallel service, controller, view, or storage folder.
- The single project map (`docs/systematic-map.mmd`) is the source of truth for what is wired and what is not. If the map shows a path is already wired, do not rewire it.

## Mandatory Read Order

1. `README.md`
2. `storage/schema/collections.json`
3. `docs/systematic-map.mmd` (the single project-map artifact — comprehensive mermaid flowchart with all routes, controllers, services, views, integrations, schema, storage, tools, and gaps)
4. The narrow GutConference skill under `.agents/skills/<skill-name>/SKILL.md` that matches the task. For admin work use the `gutconference-admin` skill.
5. When creating GitHub issues or pull requests, follow `.agents/skills/gutconference-github-issue-pr/SKILL.md`.

## Project Map as the Source of Truth

The project map is generated by `tools/generate-project-map.php` and is the single source of truth for what is wired in the codebase. It writes **one file**:

- `docs/systematic-map.mmd` — a comprehensive mermaid flowchart. Subgraphs: routes by domain (PUBLIC, AUTH, PAYMENT, SUPPORT, ADMIN), Controllers, Services, Views, Integrations, Schema collections, Storage data files, Tools, and a Gaps subgraph. Solid edges are real calls (route -> controller -> service, service -> schema collection, controller renders view, payment + Google integrations, tools regenerate / validate / smoke the map). Dashed edges (red) are missing links: unwired controllers, unwired services, unwired views, storage files with no schema, schema collections with no file.

**Do not** create a JSON, MD, or extra MMD alongside it. The single `.mmd` is the only map artifact, optimized for one read by humans and AI agents. If a future change tempts you to add `project-map.json`, `PROJECT_MAP.md`, `project-map.mmd`, `systematic-map.json`, or `systematic-map.md`, do not — extend the existing generator and let it rewrite the single file.

### When to regenerate the map

- **On every commit.** Before `git commit`, run `php tools/generate-project-map.php` and `php tools/validate-project-map.php`. The map must reflect the code in the commit.
- **Before writing a GitHub issue.** Open `docs/systematic-map.mmd`, find the relevant subgraph (controllers, services, schema, gaps), and quote the exact mermaid edge or gap node that justifies the issue. Issues must be backed by the map, not by guesswork.
- **Before pushing to `origin/main`.** The map and the validator must both be clean (no stale map, no high-severity gaps unless the user has approved them).

### How to use the map to write a good issue

For each issue you write:
1. Open `docs/systematic-map.mmd` and find the relevant subgraph.
2. Quote the exact node id, edge, or gap that proves the issue is real. If no gap is shown, the issue is not validated yet — investigate the code first.
3. The fix outline must reference existing files and existing services where possible. Do not invent new services / controllers / views / storage folders when the map shows existing code already covers the case.
4. After implementing, regenerate the map and confirm the gap is closed (or the new gap is intentional and accepted).

## User Prompt IS the Issue

The user is the customer. When the user types a prompt in chat, **that prompt is the issue** — not a request for clarification, not a discussion topic, not a meta-comment. The agent must execute the issue end-to-end:

1. **Verify the code.** Read the affected files. Quote file paths and line numbers that demonstrate the current state (and the gap, if any). Quote the project map edge or gap node that proves the issue is real. Quote the schema field that the change must respect.
2. **File the issue in Git.** One focused issue per prompt. Reference the verified files, the map edge, and the schema field. Do not bundle unverified scope.
3. **Implement the fix.** Apply the small surgical change described in the issue. Extend existing code; do not scaffold parallel services / controllers / views / storage folders. Update the schema before changing code that depends on the collection shape.
4. **Validate.** `php -l`, `php tests/run.php`, `php tools/generate-project-map.php`, `php tools/validate-project-map.php`, `php tools/smoke-local.php`. Add new tests for the new behavior.
5. **Commit and ask for push approval.** Commit with a clear message. Present a PR-style summary to the user. **Wait for explicit push approval** before `git push` — Hostinger auto-deploys to `gutconference.online` on push, so every push is a production release.

Do not invent issues out of speculation. If the user says "fix the payment flow" and the code is already correct, the answer is "the code is already correct; here is the file and line that proves it." No new service. No new view. The issue is filed, the fix is "no code change needed", the validation passes, and the prompt is closed.

Do not stop at filing the issue and wait for the user to say "now implement." The user already said so when they typed the prompt. The two-step "file then wait" loop from older versions of this guide is removed.

## Do Not Scaffold

When the existing codebase already covers a use case, **do not create a parallel implementation.** Concretely:

- If `UserContextService` already writes per-user files at `storage/user-context/{id}.json` with `user`, `bookings`, `tickets`, `appointments`, `conversations`, do not create a new `UserSupportService.php` that duplicates it.
- If `views/public/dashboard.php` already lists events/courses/registrations, do not create `views/public/my-tickets.php` that overlaps.
- If `views/admin/list.php` already lists the `support_tickets` collection, do not create a new admin support page that overlaps.
- If a service method already returns the data, the controller / view should consume it — not call a new service.

Scaffolding new files when existing code already covers the case adds tokens, increases merge risk, and breaks the user's trust.

## Enhance the Existing Generator; Do Not Create a New Tool

If the project map needs a new section (e.g. tools, integrations, gaps), extend `tools/generate-project-map.php` and the corresponding `ProjectMapService::scan()` / `renderSystematicMermaid()`. Do not create a parallel `tools/generate-systematic-map.php`. Same principle for every tool in `tools/`.

## Rules

- **Skill conflicts:** If two or more loaded skills give conflicting instructions for the same action, stop and report which skills conflict and which specific instructions overlap. Ask the user to resolve before proceeding. Do not silently pick one.
- Keep all persistent data in `storage/data/*.json`; do not introduce SQL/Postgres/MySQL unless the user explicitly requests a separate migration.
- Update `storage/schema/collections.json` before changing collection shapes, admin fields, media fields, agent-visible context, or seed data.
- Keep route -> controller -> service -> JSON-store boundaries.
- Do not add React, CDN React, SPA shells, or a second frontend or parallel implementation.
- Build UI with modern HTML/CSS, JSON-backed data, and `storage/schema/collections.json`. PHP runs the shared-hosted app and binds data for routing, services, validation, persistence, and shared-hosting data binding; it should not drive the visual design model. Do not introduce a frontend framework unless explicitly requested.
- Read `Design.md` before broad UI changes; use its GutConference-adapted Neuform comparison for density, motion, color, and component direction. For UI-only refactors, preserve visible text/content meaning unless the user explicitly asks for copy changes.
- Public users must not be able to create conferences. Only admins create and publish events.
- Admin mutations should be auditable.
- Event media should use the media library picker/upload flow.
- Environment and storage permission changes belong in `/admin/environment`, but do not introduce project `.env` files. Do not use, create, restore, or track `.env`, `.env.example`, or other `.env.*` files. Secrets must be configured through encrypted admin integrations in `storage/data/adminsecrets.json` or server-level environment configuration outside the repo. If a rebase reports env-file conflicts, keep the GitHub `main` deletion.
- Admin integration secrets must be saved through `SecretService` into encrypted `storage/data/adminsecrets.json`. Do not model secrets in `collections.json`. Keep secret files git-ignored and out of public views.
- Keep admin navigation lean. Prefer grouped admin sections and automatic defaults over adding one-off menu items for every small action. Group Events & Classes, Page Sections, Speakers, Agenda, Venues & Maps, and Registrations under Event Management.
- Maximize automation from event/data: derive labels, countdown/timer values, remaining seats, and notification timing from event date/time, timezone, ticket capacity, and paid registrations. Store timezone once in event/settings context. Only expose fields in admin that need human judgment; generated labels, counters, queue timings, and derived availability should be computed by PHP services or scripts.
- Compare public event UX against provided competitor/reference URLs, but keep the result corporate, clinical, luxury, credible, and profile-first.
- Each event/class must expose a payment mode: external Razorpay payment page link or internal Razorpay integration. Payments require login first.
- Customer signup is Google OAuth-first so Google Calendar reminders can be created for buyers without a second OAuth step. Manual password users are legacy/dev fallback; keep SMTP forgot-password reset support for them, but require Google connection before payment.
- Use `php -S 127.0.0.1:6040 index.php` as the default local server command unless the port is already occupied.
- When the product evolves, update the matching GutConference skill files under `.agents/skills/` so future agents inherit new workflow rules.
- When working from a pull request, review previous PR comments, push fixes to the same remote branch when appropriate, and communicate PR follow-up clearly to the remote collaborator by email or the configured project communication channel when requested.
- One project map file only: `docs/systematic-map.mmd`. Do not create `project-map.json`, `PROJECT_MAP.md`, `project-map.mmd`, `systematic-map.json`, or `systematic-map.md`.
- One tool per concern. Extend the existing tool, do not create a new one.

## Validation

Run the smallest useful validation for the change. **Always regenerate and validate the project map** because every code change can affect wiring:

```bash
php -l path/to/changed.php
php tests/run.php
php tools/generate-project-map.php
php tools/validate-project-map.php
```

For UI changes, use a browser workflow and check home, event detail, admin login, and the changed admin resource.

## Deployment / Push to Production

Pushing to `origin/main` auto-deploys to **gutconference.online** via Hostinger Git auto-deploy. Treat every push as a production release.

The production remote for this repo is GitHub `getwinharris/GutConference-phpCMS.git`. Before comparing, rebasing, validating a release, or saying the branch is current, make sure `origin` points there and fetch GitHub `main` directly:

```bash
git remote set-url origin https://github.com/getwinharris/GutConference-phpCMS.git
git fetch --prune origin +refs/heads/main:refs/remotes/origin/main
git branch --set-upstream-to=origin/main main
```

Treat `refs/remotes/origin/main` as valid only after that forced GitHub fetch. Do not trust a pre-existing local `origin/main` ref from this machine, because the project was created locally before being pushed to GitHub. Use the freshly rebuilt GitHub remote-tracking ref as the baseline. If GitHub `main` moved, rebase local commits onto the fetched remote branch and resolve conflicts in favor of the current secret policy: tracked `.env` files stay deleted and are not reintroduced.

### Before opening a PR, the agent MUST:

1. **Create a branch** for the fix:
   ```bash
   git checkout -b fix/issue-19-smoke-test-pollution
   ```

2. **Commit changes** on the branch with a clear message referencing the issue.

3. **Run validation:**
   ```bash
   php -l path/to/changed.php
   php tests/run.php
   php tools/generate-project-map.php
   php tools/validate-project-map.php
   ```

4. **Push the branch** to origin:
   ```bash
   git push origin fix/issue-19-smoke-test-pollution
   ```

5. **Draft a PR title and body** describing the issue and precise changes per file. No agent instructions or internal checklist.

6. **Present the PR draft to the user** for confirmation before creating it.

7. **Create the PR** once confirmed:
   ```bash
   gh pr create --title "..." --body "..." --base main
   ```

8. **Report the PR URL** and wait for merge approval.

### After merging:

- Confirm the merge and remind the user to verify the live site at `https://gutconference.online`.
